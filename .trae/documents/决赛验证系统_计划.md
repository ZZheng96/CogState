# 决赛验证系统计划（在 vis 基础上扩展）

## Context

现状：前端指标读取缓存中的逐帧分数，每次请求都用 `model_eval.metrics` 重新计算。问题在于各方案自带的标签 y 不一致：
- current 方案的 y 由 events 生成（`system/web/model_eval.py:_labels`）；
- E42/E44 的 y 直接借用 sliding1 的标签；
- 帧网格也不同：current 从 t=6 开始，E44 从 t=66 开始。

因此方案之间不能严格对比。决赛流程是：现场采集 → 调试时间内适配模型 → 上交推理程序 → 主办方在新被试上按 bACC/AUC 评分。系统需要覆盖以下环节：
- 导入数据；
- 用黑盒方式做分块流式推理并实时回放；
- 按统一口径独立计算指标、检查合规；
- 重训模型；
- 导出提交包。

已确认的选择：
- 实时数据源先做 BDF 文件回放，设备留适配器接口；
- 系统包含训练；
- 指标采用黑盒统一口径；
- 继续使用标准库 HTTP + SSE，不引入新依赖。

## 架构

新增 `system/` 包作为后端核心，`system/web/viewer_server.py` 作为 HTTP 层调用它。

| 模块 | 职责 | 复用 |
|---|---|---|
| `system/dataset.py` | 数据源登记：内置 `EEG_dataset/` 和导入目录 `data_import/<名称>/`（BDF + events.csv）。负责校验文件、对齐时间、生成 trial 与 BAD 区间 | `src/eeg_decoder.load_bdf`、`src/cogstate.load_trials` |
| `system/truth.py` | **独立真值**：只读 BDF 和 events，给定任意决策时刻 t 返回 y（窗口 [t−6, t] 完全落在单个 trial 内且不含 BAD 时取 0/1，否则为 −1） | 从 `model_eval._labels` 迁出，作为唯一实现 |
| `system/evaluate.py` | **黑盒评估**：输入方案输出的 (t, score)，用 truth 打标签，计算 bACC/AUC/F1/≥0.9 人数（逐人与宏平均），并给出覆盖率，即有效帧中有输出的比例。缺失帧不计入指标，单独报告 | 从 `model_eval.metrics` 迁出 |
| `system/compliance.py` | 合规检查：①前缀不变性，截断未来数据后历史输出不变；②分块一致性，chunk 取 1/250/1000 时输出相同；③感受野检查，在 t−6 s 之前注入扰动、在其后清零，检查原始分数是否变化；④速度，测实时倍率 | 参考 `test/17_compliant/test_streaming.py`、`test/44_late_drift/verify_infer_dt.py` |
| `system/runner.py` | **流式运行器**：把 bundle 包装成 `Decoder` 协议（`reset()`、`update(chunk_v)` 返回 `[(t, score, state)]`）。数据源 `Source` 协议目前有 `FileReplay(bdf, speed)` 一种，后续可加 `DeviceSource`，现在只留接口。输出写入缓存 npz，同时通过 SSE 推送 | `src/infer.py` 的 `stream_outputs`、`StreamingInference`、`PostProcessor` |
| `system/train.py` | 重训：对选中的数据集合（训练集 + 导入数据）提取滑窗特征 → `train_bundle` → 生成 `models/<名称>.pt`。用后台任务运行，日志推送到前端 | `test/11_individual_20261102/build_sliding.py`、`test/17_compliant/streaming.train_bundle` |
| `system/export.py` | 导出提交包：`src/`、依赖的 streaming 模块、选定模型、`运行说明.md`、最小运行示例与对应输出，打包为 zip，并运行一次自检（解压到临时目录后跑示例 CLI，比对输出） | `运行说明.md`、`src/infer.py` CLI |
| `system/jobs.py` | 后台任务队列：GPU 任务串行执行，每个任务有状态、进度和日志 | 替代 `viewer_server` 中的 `PENDING`/`start_pred` |

方案注册表 `system/web/schemes.py` 改成两类：
- **可运行方案**：给出 bundle 和后处理配置，由 runner 生成输出；
- **离线分数方案**：如 E42/E44，只提供 (t, score)。

两类方案的 y 都不再自带，统一由 truth 生成。E44 缓存去掉 y 字段，`build_e44.py` 只写 t 和 score。

## 前端（system/web/viewer.html 增加标签页）

1. **查看**：现有功能。指标改为调用 `/api/eval`，并显示覆盖率。
2. **实时回放**：选择数据源、被试、方案和倍速（1×/10×/最快），点击开始。SSE 逐秒推送决策，波形自动滚动，得分条和真值条同步增长，指标卡显示累计 bACC/AUC 并实时刷新，同时显示延迟和实时倍率。
3. **评估**：选择方案和被试集合，运行黑盒评估和合规检查，生成逐人表与宏平均，可导出 md/CSV 报告。报告写明 AUC 和 F1。
4. **数据与训练**：导入 BDF 和 events 并校验，可看到 trial 和 BAD 预览；选择训练集合后启动重训，查看日志；训练好的模型自动注册为可运行方案。
5. **导出**：选择模型 → 生成提交 zip → 显示自检结果。

## 实施顺序

1. truth、evaluate 抽出，并改造 schemes 为统一口径。验证：current 的指标与改造前一致（.947/.989/.947）；E44 按新口径重算后与报告值（.782/.832/.774）的差异要说明清楚。
2. runner + SSE + 实时回放标签页。
3. compliance + 评估标签页 + md 报告导出。
4. dataset 导入 + train + 训练标签页（需要先确认 build_sliding 与流式特征一致）。
5. export + 自检。
6. 更新 `system/web/报告_查看器与当前方案评估.md`，加入系统使用说明。每完成一步都 commit 并 push。

## 验证

- 统一口径：用 current 方案对照旧值；在 E44 上交叉检查帧对齐（同一时刻的 y 应一致）。
- 回放：选 018，用最快倍速跑完整条记录，输出应与 `model_eval.compute` 的缓存逐帧相同；1× 倍速下延迟小于 1 s。
- 合规：current 方案四项检查全部通过；再构造一个违规方案（双向平滑），检查能否被识别出来。
- 训练：用 57 人重训，得到的 bundle 与现有 `model_bundle.pt` 的训练集 bACC 应在 ±0.005 以内；用一个被试模拟导入的新数据，跑通全流程。
- 导出：解压 zip，在干净目录用 `.venv` 跑示例 CLI，输出与系统一致。
- 浏览器端：用子 agent 逐个验证 5 个标签页。
